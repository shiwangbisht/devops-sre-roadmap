# AWS S3 — everything an SRE should know

## What S3 actually is

**Object storage**, not a filesystem and not a block device — you don't mount it, you PUT/GET whole
objects (files) identified by a **key** (the full "path" string, e.g. `logs/2026/10/app.log`) inside a
**bucket** (a globally-unique-named top-level container). There's no real folder hierarchy — the `/` in
keys is just a convention the console renders as folders; underneath, it's a flat key-value store.

- **Durability: 11 nines (99.999999999%)** — achieved by redundantly storing objects across multiple
  AZs within a region automatically. This is *durability* (won't lose the data), not *availability*
  (whether you can reach it right now) — know the difference, it's a classic interview distinction.
- **Unlimited scale** — no capacity planning the way you'd think about EBS/disk sizing.
- **Regional** — a bucket lives in one region (though accessible globally via the right endpoint).

## Core features & options (the toolbox)

### Storage classes — the single biggest cost lever

| Class | Use case | Retrieval | Min storage duration |
|---|---|---|---|
| **Standard** | Frequently accessed, default | Instant | None |
| **Intelligent-Tiering** | Unknown/changing access patterns | Instant | None (small monitoring fee) |
| **Standard-IA** | Infrequent access, still needs instant retrieval | Instant | 30 days |
| **One Zone-IA** | Infrequent, recreatable data (not critical) | Instant | 30 days |
| **Glacier Instant Retrieval** | Archive, accessed ~quarterly, needs instant access | Instant | 90 days |
| **Glacier Flexible Retrieval** | Archive, rarely accessed | Minutes–hours | 90 days |
| **Glacier Deep Archive** | Long-term compliance/backup, almost never accessed | Hours (12h std) | 180 days |
| **Express One Zone** | Latency-sensitive, high-throughput (ML training, analytics) | Single-digit ms | None |

**SRE rule of thumb:** if you don't know the access pattern, start with **Intelligent-Tiering** — it
auto-moves objects between tiers based on actual access and removes the guesswork, at a small monitoring
fee per object. Hand-picking tiers makes sense once you *know* the pattern (e.g. logs: hot for 30 days,
then cold).

### Versioning

Keeps every version of an object instead of overwriting on PUT, and keeps a "delete marker" instead of
truly deleting on DELETE (the old version is still recoverable). Protects against accidental
overwrite/delete — including *malicious* delete, since a delete just adds a marker unless the caller also
has permission to permanently remove versions (`s3:DeleteObjectVersion`). Cost tradeoff: every version is
billed as its own object, so pair with a lifecycle rule that expires noncurrent versions.

### Lifecycle rules

Automated rules to **transition** objects between storage classes or **expire** (delete) them based on
age — e.g. "move to Standard-IA after 30 days, Glacier after 90, delete after 365." This is *the*
mechanism for turning "we never delete anything, just in case" into something that doesn't bankrupt the
storage bill.

### Replication (CRR / SRR)

- **Cross-Region Replication (CRR)** — automatically copy objects to a bucket in another region.
  Use cases: disaster recovery, data residency/compliance, latency (serve from a region close to users).
- **Same-Region Replication (SRR)** — copy within the same region. Use cases: aggregating logs from
  multiple buckets into one, maintaining a copy in a different account for separation of duties.
- Requires versioning enabled on both source and destination.

### Object Lock (WORM)

Write-Once-Read-Many — makes objects genuinely immutable for a retention period (even the root account
can't delete them under `Compliance` mode). Used for regulatory/compliance requirements (financial
records, audit logs) where "someone with console access deleted it" must be impossible, not just
discouraged.

### Other features worth knowing by name

- **Multipart upload** — splits large objects (>100MB recommended, required >5GB) into parts uploaded in
  parallel, resumable on failure — how large files actually get uploaded reliably.
- **Presigned URLs** — a time-limited URL granting temporary access to a private object without making it
  public or sharing credentials — common for "let a user download this one file for 15 minutes."
  `aws s3 presign s3://bucket/key --expires-in 900`
  
- **S3 Event Notifications** — trigger Lambda/SQS/SNS on object create/delete — the backbone of most
  "process a file when it lands in S3" pipelines.
- **S3 Select** — run a SQL-like query against part of an object (e.g. a CSV/JSON/Parquet file) without
  downloading the whole thing — cheaper and faster for "I just need 3 columns of this 2GB file."
- **Static website hosting** — serve a bucket's contents directly as a website (public `index.html`
  etc.) — common for simple static sites, usually fronted by CloudFront in front rather than used bare.
- **Transfer Acceleration** — routes uploads through CloudFront edge locations for faster transfer over
  long distances — relevant for large uploads from geographically distant clients.
- **Access Points** — named network endpoints with their own policy, for simplifying access management
  when many applications/teams share one bucket.

## Use cases (the "when would I actually reach for this" list)

- **Static assets / website hosting** — images, JS/CSS bundles, usually behind CloudFront.
- **Data lake** — raw + processed data for analytics (Athena, EMR, Redshift Spectrum query S3 directly).
- **Backup & disaster recovery** — database snapshots, config backups, often paired with CRR + Glacier.
- **Log storage** — ALB/CloudTrail/VPC Flow Logs land here by default; lifecycle rules keep cost sane.
- **Application state/artifacts** — Terraform state (with DynamoDB locking), CI/CD build artifacts,
  container image layers (some registries use S3 under the hood).
- **Media storage & processing pipelines** — upload triggers a Lambda (via Event Notifications) to
  transcode/resize, classic serverless pipeline shape.

## Security — what an SRE is actually responsible for getting right

- **Block Public Access** — account- and bucket-level settings that override any policy trying to make
  something public. **Leave this ON by default**; a bucket should only ever be deliberately made public
  with a clear, reviewed reason (e.g. a static website bucket).
- **Bucket policy vs. IAM policy vs. ACL:**
  - **IAM policy** — attached to a user/role, says what *that identity* can do (can span multiple buckets).
  - **Bucket policy** — attached to the bucket itself, says who can access *this bucket* (including
    cross-account access) — resource-based, the bucket's own door rules.
  - **ACL** — legacy, object/bucket-level, mostly superseded by the above two; AWS now recommends
    disabling ACLs entirely on new buckets.
- **Encryption at rest:**
  - **SSE-S3** — AWS manages the keys entirely, simplest, encryption on by default for all new buckets.
  - **SSE-KMS** — AWS KMS-managed keys, gives you key rotation policy, access logging on key usage, and
    the ability to revoke access by disabling the key — the one to reach for when you need an audit
    trail of *who decrypted what, when*.
  - **SSE-C** — customer-supplied keys, AWS never stores the key — you manage key custody entirely.
- **Encryption in transit** — enforce via a bucket policy that denies non-HTTPS requests
  (`aws:SecureTransport` condition).
- **VPC endpoint (Gateway type, free)** — lets resources in a VPC reach S3 without traversing the public
  internet/NAT gateway — both a security and cost win (no NAT data processing charges for S3 traffic).
- **Access logging** — bucket-level server access logs, or CloudTrail data events for S3 API calls (who
  called `GetObject` on what, when) — essential for any security investigation.
- **Least privilege** — scope IAM/bucket policies to specific prefixes/actions
  (`s3:GetObject` on `arn:aws:s3:::bucket/logs/*`), not `s3:*` on `*`.

## Cost — what actually drives the bill

- **Storage cost** — per GB/month, varies by storage class (this is the lever lifecycle rules pull).
- **Request cost** — PUT/COPY/POST/LIST requests cost more per-request than GET; high-request-volume
  workloads (e.g. millions of small objects) can rack up request costs even if total data is small.
- **Data transfer OUT** to the internet costs money; transfer IN and transfer to CloudFront/same-region
  AWS services is free or cheap — a classic design lever (serve via CloudFront, not direct S3 egress).
- **Early deletion/retrieval fees** — IA and Glacier classes charge a penalty if you delete/transition an
  object before its minimum storage duration, or charge extra for faster-than-standard retrieval from
  Glacier. Moving short-lived objects straight to Glacier is a common costly mistake.
- **Versioning cost trap** — every version is billed as a full object; without a lifecycle rule to expire
  noncurrent versions, a frequently-overwritten versioned bucket can silently balloon in cost.
- **Visibility tools** — S3 Storage Lens (usage/activity metrics across buckets/accounts) and Cost
  Explorer (filtered to S3) are how you actually find out what's driving the bill before guessing.

## Migration — getting data into (or between) S3

- **`aws s3 sync` / `aws s3 cp`** — CLI-level, fine for small-to-medium data over a decent connection.
- **AWS DataSync** — managed, scheduled/continuous transfer from on-prem (NFS/SMB) or another cloud into
  S3, with validation and bandwidth throttling — the real answer for "sync this file share into S3 on an
  ongoing basis," not a cron job wrapping `aws s3 sync`.
- **AWS Snowball / Snowball Edge / Snowmobile** — physical devices for genuinely large (TB–PB) one-time
  migrations where network transfer would take weeks; Snowmobile is the shipping-container-scale option.
- **Storage Gateway** — hybrid option, presents S3 as an on-prem NFS/SMB share or iSCSI volume — for
  gradually moving workloads without rewriting applications to speak S3's API directly.
- **Cross-region/cross-account migration** — S3 Batch Operations or CRR, rather than scripting a loop of
  `aws s3 cp` calls yourself for large object counts.

## Manual steps (console + CLI) — do this yourself first, per the learning plan

**Safety first:** confirm you're in the learning AWS account before anything else:
```bash
export AWS_SHARED_CREDENTIALS_FILE=~/.aws/credentials_terraform
aws sts get-caller-identity   # must show Account: 003720987974
```

### Console path
1. S3 → **Create bucket** → name it `shiwang-tf-learning-<today's date>` (globally unique) → region
   `us-east-1` → leave **Block all public access ON** (default, don't touch it for this exercise).
2. On the creation form (or after, under **Properties**), enable **Bucket Versioning**.
3. Go to the **Management** tab → **Create lifecycle rule** → name it, scope to the whole bucket → add
   a transition action (e.g. "move current versions to Standard-IA after 30 days") and/or an expiration
   action (e.g. "expire noncurrent versions after 30 days").
4. Upload one throwaway file via **Upload**, then overwrite it with a second version — go check the
   **Versions** view (toggle "Show versions") to see both versions listed.

### CLI path (same result, by hand)
```bash
BUCKET=shiwang-tf-learning-$(date +%Y%m%d)

aws s3api create-bucket --bucket "$BUCKET" --region us-east-1

aws s3api put-bucket-versioning \
  --bucket "$BUCKET" \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-lifecycle-configuration \
  --bucket "$BUCKET" \
  --lifecycle-configuration '{
    "Rules": [{
      "ID": "expire-noncurrent-versions",
      "Status": "Enabled",
      "Filter": {},
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 }
    }]
  }'

echo "hello v1" > test.txt
aws s3 cp test.txt "s3://$BUCKET/test.txt"
echo "hello v2" > test.txt
aws s3 cp test.txt "s3://$BUCKET/test.txt"

aws s3api list-object-versions --bucket "$BUCKET"   # see both versions
```

Once done: note the bucket name + what you observed in
`05-terraform-iac/learning/practical_log.md` — next step is importing this exact bucket into Terraform.

## Interview questions (with the short answer you should be able to give cold)

1. *What's the difference between S3's durability and availability guarantees?* — Durability (11 9s) is
   about not losing the data (redundant storage across AZs); availability is about whether you can
   access it *right now* (varies by storage class, e.g. One Zone-IA has lower availability since it's
   not multi-AZ). A bucket can be 100% durable but briefly unavailable during an AZ event.
2. *When would you choose Intelligent-Tiering over manually picking a storage class?* — When access
   patterns are unknown or change over time — it auto-moves objects based on actual access, removing the
   guesswork, at a small per-object monitoring fee. Manual tiering makes sense once the pattern is known
   and stable (e.g. logs always go cold after 30 days).
3. *Does S3 Versioning protect against a malicious delete?* — Mostly — a DELETE just adds a delete
   marker, the old version is recoverable — unless the caller also has `s3:DeleteObjectVersion`
   permission to permanently remove versions, which should be tightly restricted separately from normal
   delete permission.
4. *What's the difference between a bucket policy and an IAM policy, and when would you need both?* —
   IAM policy is attached to an identity (user/role) and can span multiple buckets; bucket policy is
   attached to the bucket and controls access to *that* bucket, including cross-account access. You need
   a bucket policy specifically for cross-account access since the other account's IAM policy alone can't
   grant access to a bucket it doesn't own.
5. *Why would you use SSE-KMS instead of the default SSE-S3?* — When you need an audit trail of key
   usage (who decrypted what, via CloudTrail), rotation policy control, or the ability to revoke access
   by disabling the KMS key — SSE-S3 is simpler but gives none of that visibility/control.
6. *What's a VPC Gateway endpoint for S3, and why would you use one?* — Lets resources inside a VPC
   reach S3 without the traffic going over the public internet or through a NAT gateway — both tightens
   security (no public routing) and cuts cost (NAT data processing charges avoided).
7. *What's the early-deletion-fee trap with Glacier/IA classes, and how do you avoid it?* — These classes
   bill a penalty if an object is deleted/transitioned before its minimum storage duration (30/90/180
   days depending on class) — avoid by not lifecycle-transitioning short-lived objects straight to a deep
   archive tier.
8. *Why can a versioned bucket's cost silently balloon over time?* — Every version is billed as a full
   object; without a lifecycle rule expiring noncurrent versions, frequently-overwritten objects
   accumulate unbounded storage cost from old versions nobody's using.
9. *How would you migrate 50TB from an on-prem NFS share into S3?* — Not `aws s3 sync` over a WAN link —
   either AWS DataSync for a managed, ongoing/scheduled transfer, or Snowball/Snowball Edge if network
   transfer time is prohibitive and a one-time physical shipment is faster.
10. *Why is Object Lock different from just restricting delete permissions via IAM?* — IAM-based
    restriction can still be changed by someone with sufficient privilege (e.g. an admin); Object Lock in
    Compliance mode makes deletion genuinely impossible for the retention period, including for the root
    account — needed when the requirement is regulatory immutability, not just access control.

## Scenario-based questions (the "what would you actually do" kind)

1. *A dev says "just make the bucket public so the frontend team can pull the assets."* — Don't disable
   Block Public Access account-wide for convenience. Either front it with CloudFront (keep the bucket
   private, use an Origin Access Control so only CloudFront can read it) for a public-facing use case, or
   scope a bucket policy/presigned URLs if it's meant for a specific internal team, not the whole internet.
2. *Storage costs tripled this month and nobody changed the application.* — Check S3 Storage Lens/Cost
   Explorer first, not guess. Common causes: a lifecycle rule that was supposed to transition/expire
   objects got removed or misconfigured, versioning turned on without an expiration rule, or a new
   high-volume write workload landed in the bucket (check request-count metrics too, not just storage).
3. *Compliance says audit logs must be retroactively tamper-proof for 7 years.* — Object Lock in
   Compliance mode with a 7-year retention period, not just IAM restrictions — the requirement is
   "nobody, including an admin, can delete or alter it," which only Object Lock in Compliance mode
   actually guarantees.
4. *An app team wants to share a private S3 bucket with another AWS account for one migration project,
   then revoke access after.* — Bucket policy granting the specific external account/role scoped access
   (not public, not IAM in their account since they don't own the bucket), time-boxed by removing the
   policy statement when the migration's done — avoid leaving standing cross-account access around after
   the need ends.
5. *A pipeline needs to process files the moment they land in a bucket, at high volume.* — S3 Event
   Notifications → Lambda (or SQS if you need buffering/retry control under bursty load) rather than
   polling the bucket on a schedule — event-driven avoids both the latency and the wasted LIST-request
   cost of polling.
6. *You're asked why the team should move Terraform state from local files to S3.* — Team collaboration
   (shared source of truth) and locking (via DynamoDB) to prevent concurrent applies corrupting state —
   tie this back to [state_management.md](../../05-terraform-iac/learning/state_management.md), same
   backend pattern.
